# 模块化核验流水线升级说明

本文同步 MiMo Trust 从旧版下游核验实现升级为 `compact-claims-v2 + M1–M7` 模块化流水线后的工程状态，供后端、Web、Android、测试和运维人员共同使用。

本文描述的是当前仓库已经实现的行为，不是未来规划。入口实现位于 `backend/app/trust/service.py`，模块代码位于 `backend/app/trust/pipeline_v2/`。

## 1. 升级目标

本次升级主要解决旧流水线的五类问题：

1. 上游“原子主张、新闻事实、隐性观点”语义重叠，进入下游前还需要额外转换；
2. 搜索提供方和返回结构过多，慢请求、失败隔离及证据审计难以统一；
3. 候选证据经过机械规则提前淘汰，有价值材料可能无法进入最终研判；
4. 中间结果、模型原始输出、耗时和用量缺少统一的按案例运行目录；
5. Web 与 App 只能在任务结束后看到结果，完整报告字段没有全部展示。

升级后的原则是：

- 上游直接输出最小、稳定、可核验的主张协议；
- 搜索数量不因性能优化而减少，所有查询一次性并发执行；
- 单条搜索独立超时，失败不能拖死整批任务；
- 程序只负责结构校验、编号、去重、调度和渲染，语义判断交给 LLM；
- 不按人物、学校、行业、真假案例或网站名单硬编码结论；
- 每个阶段都有明确输入、输出和可独立检查的落盘产物；
- 面向短视频传播风险粗筛，证据不足时优先标记待核实，而不是轻率判真；
- 快速与高质量档位使用相同查询和证据，只改变最终研判的思考强度。

## 2. 总体架构

```mermaid
flowchart LR
    A[URL / 分享文本 / 文字 / 文件] --> B[内容解析、字幕、ASR、OCR]
    B --> C[MiMo 主张提取]
    C --> D[compact-claims-v2]
    D --> M1[M1 校验与编号]
    M1 --> M2[M2 检索规划]
    M2 --> M3[M3 Exa 并发检索]
    M3 --> M4[M4 证据归一化]
    M4 --> M5[M5 MiMo Pro 并发初筛]
    M5 --> M6[M6 MiMo Pro 综合研判]
    M6 --> M7[M7 JSON / Markdown 渲染]
    M7 --> W[Web 完整报告]
    M7 --> J[Job API + SSE]
    J --> P[Android 结论卡与报告详情]
```

上游内容解析继续负责平台适配、短链安全展开、字幕、ASR、OCR 和画面信息。模块化核验流水线只接收已经提取好的主张 JSON，因此两部分可以独立演进。

## 3. 上下游数据契约

### 3.1 协议版本

对外协议版本为 `compact-claims-v2`，对应 Pydantic 模型 `StructuredInformation`：

```json
{
  "主题": "质疑某项新闻数据的真实性与合规性",
  "主张": [
    {
      "文本": "新闻报道称某人在21年间累计完成300次无偿献血。",
      "表达": "转述"
    },
    {
      "文本": "该献血频次涉嫌违反相关规定并可能属于履历包装。",
      "表达": "隐含"
    }
  ]
}
```

字段约束：

| 字段 | 类型 | 约束 |
|---|---|---|
| `主题` | 字符串 | 非空，用一句话概括内容讨论的核心问题 |
| `主张` | 数组 | 可为空；为空表示没有现实世界事实需要外部核验 |
| `主张[].文本` | 中文字符串 | 自包含、可独立理解和核验，不依赖原字幕位置 |
| `主张[].表达` | 枚举 | 仅允许 `直接`、`转述`、`隐含` |

完全相同的“文本 + 表达”会在服务端去重。服务端不替上游改变“可能、涉嫌、全部、唯一、严重”等限定词。

### 3.2 为什么不再保留旧字段

新版不再输出以下字段：

- `case_id`：案例编号由服务端根据来源 URL 或规范化 JSON 生成；
- `内容主题`：统一为更短的 `主题`；
- `原子主张`、`新闻事实`、`隐性观点`：统一拍平成 `主张`，表达方式保存在每项的 `表达` 字段。

这样能避免同一事实同时出现在多个数组中，也避免为了兼容旧协议再调用一次模型转换。

### 3.3 无需核验的内容

纯娱乐、虚构角色剧情、游戏解说、作品情节分析等内容，如果没有现实世界的事实性主张，上游输出空 `主张`：

```json
{
  "主题": "动画角色剧情解析",
  "主张": []
}
```

核验服务直接返回：

```json
{
  "status": "skipped",
  "message": "当前内容没有需要外部事实核验的现实世界主张。"
}
```

该路径不调用 M2–M7，也不消耗 Exa。

## 4. M1–M7 模块说明

### 4.1 M1：输入规范化与稳定编号

类型：纯程序。

输入：案例目录中的 `input.json`。

职责：

- 验证 `主题`、`主张[].文本` 和 `主张[].表达`；
- 拒绝未知字段和非法表达枚举；
- 为主张按输入顺序分配稳定编号 `C1`、`C2`；
- 保存原始输入和正式主张产物。

主要输出：`01_claims.json`。

M1 不理解真假，不拆分或改写主张，也不对内容做领域判断。

### 4.2 M2：检索规划与核验需求

类型：一次 MiMo 2.5 调用，关闭思考。

输入：`01_claims.json`。

职责：

- 将每条主张映射到至少一个核验项 `V1`、`V2`；
- 描述每个核验项的问题和所需证据；
- 为核验项生成查询 `Q1`、`Q2`；
- 区分“某说法被报道”与“报道内容真实”；
- 为夸大、违规、造假、摆拍、动机等指控建立独立核验需求；
- 一次性形成全部查询，不依赖后续二次检索。

查询数量由程序给出确定预算：

```text
min(MAX_QUERY_COUNT, max(MIN_QUERY_COUNT, 主张数 + 3))
```

默认最少 5 条、最多 12 条。验证器要求：

- 全部 `C` 编号被核验项覆盖；
- 全部 `V` 编号被查询覆盖；
- 查询数量与预算完全一致；
- 不存在重复编号和完全相同查询；
- 渠道只允许 `网页` 或 `学术`。

“网页/学术”是检索意图，不代表使用不同提供方；M3 当前统一通过 Exa 执行。

主要输出：

- `02_planning_input.json`：实际发送给模型的消息、参数和提示词；
- `02_planning_output.json`：模型原始文本及响应信息；
- `02_planning_metrics.json`：耗时、token 和错误；
- `02_verification_plan.json`：校验通过的正式检索计划。

### 4.3 M3：并发检索执行

类型：纯程序调度 + Exa API。

输入：`02_verification_plan.json`。

执行方式：

- 每个 `Q` 查询展开为一个稳定任务 `T`；
- 所有任务通过 `asyncio.gather` 一次性并发；
- 每个任务拥有独立超时和错误状态；
- 单个查询超时、HTTP 错误或返回异常不会取消其他任务；
- 默认每个查询返回 5 条、单任务超时 10 秒；
- 默认请求 `type=auto` 和 highlights，避免抓取无限全文。

当前只保留 Exa 提供方。OpenWebSearch、OpenAlex、ArXiv、Wikipedia、Semantic Scholar 等旧适配器已移除；学术、法规、官方记录等来源通过 M2 查询语义引导 Exa 检索。

主要输出：

- `03_retrieval_input.json`：正式计划及展开后的全部任务；
- `03_retrieval.json`：逐任务状态和 Exa 原始响应；
- `03_retrieval_metrics.json`：任务数、结果数、状态分布和 Exa 返回费用。

### 4.4 M4：证据池归一化

类型：纯程序。

输入：`03_retrieval.json`。

职责：

- 从 Exa 原始响应提取标题、URL、日期、作者和 highlights；
- 只接受合法 HTTP(S) URL；
- 统一协议、主机、默认端口和空路径；
- 移除 URL fragment、`utm_*` 等跟踪参数；
- 按规范化 URL 精确去重；
- 合并同一 URL 对应的任务、查询、核验项和渠道关系；
- 为证据分配稳定编号 `E1`、`E2`。

M4 明确不执行：

- 按标题相似度合并不同 URL；
- 判断网站可信或不可信；
- 根据关键词判断证据支持或反驳；
- 删除“看起来像营销号”的材料。

这些语义判断统一留给 M5/M6，以避免小型机械名单造成误杀。

主要输出：

- `04_normalization_input.json`：来源文件哈希、任务摘要和归一化规则；
- `04_evidence_pool.json`：完整统一证据池；
- `04_normalization_metrics.json`：原始数量、无效链接和去重统计。

### 4.5 M5：并发证据初筛

类型：MiMo 2.5 Pro，多批次并发，关闭思考。

输入：

- `01_claims.json`；
- `02_verification_plan.json`；
- `04_evidence_pool.json`。

职责：

- 按字符预算将完整证据池分块；
- 并发判断每条 `E` 证据的来源性质和独立性；
- 标注与最多两个关键主张的关系；
- 标注支持、反驳、背景或仅证明传播；
- 标注直接或间接；
- 识别转引、重复和循环引用风险；
- 决定 M6 接收全文 `F` 还是摘要卡 `K`。

M5 的紧凑行协议示意：

```json
{
  "rows": [
    ["E1", "O", "D", [["C2", "R", "D"]], "F", "", "规则原文仅适用于特定对象"]
  ]
}
```

每个证据编号必须出现在账本中。M5 负责压缩而不是终判，M6 会重新检查账本和选入的全文。

主要输出：

- `05_attempts/Axx/`：每批模型输入、原始输出和 metrics；
- `05_evidence_ledger.json`：覆盖完整证据池的统一初筛账本。

### 4.6 M6：最终研判

类型：一次 MiMo 2.5 Pro 调用；非法或不完整输出可重试。

输入：

- 全部 `C` 主张；
- M2 核验计划；
- 覆盖全部 `E` 的 M5 初筛账本；
- M5 选择为 `F` 的证据全文信息；
- `K` 级证据摘要卡。

职责：

- 逐主张输出结论、证据充分度、依据和不确定性；
- 重新检查 M5 可能产生的关系误判；
- 识别不同媒体是否只是循环引用同一来源；
- 保持输入主张中的范围、时间、数量和限定词；
- 区分基础事实与附加指控；
- 判断输入整体是否通过反讽、剪辑、错误前提或概念混淆形成引导；
- 输出传播建议和待补证据。

允许的整体结论为：`可信`、`大体可信`、`真假混合`、`误导`、`不实`、`证据不足`。

允许的逐主张结论包括：`属实`、`部分属实`、`误导`、`虚假`、`待核实`、`缺乏证据` 等报告协议值。

程序会验证：

- 恰好覆盖全部 `C` 编号；
- 只能引用已有 `E` 编号；
- 整体关键证据必须至少出现在一条逐主张依据中；
- JSON 结构、枚举和字段完整；
- 不得重复或伪造证据编号。

若输出不是合法 JSON、因 token 上限截断或违反完整性约束，流水线只重试 M6，复用已经完成的 M1–M5 和证据池，不重新搜索。默认最多尝试 2 次。

主要输出：

- `06_attempts/Axx/`：每次请求、原始输出和 metrics；
- `06_report_draft.json`：验证通过的正式报告草稿。

### 4.7 M7：报告验证与渲染

类型：纯程序。

输入：`06_report_draft.json`、M1 主张和 M4 证据池。

职责：

- 把报告中的 `E` 编号解析为标题、URL、日期和作者；
- 再次检查整体关键证据与逐主张依据的一致性；
- 生成前端使用的完整报告 JSON；
- 生成便于人工阅读和归档的 Markdown；
- 汇总 M1–M7 耗时、LLM 调用、token 和 Exa 用量。

报告顶层结构：

```json
{
  "整体判断": {},
  "主张核验": [],
  "叙事分析": {},
  "待补证据": []
}
```

主要输出：

- `07_render_input.json`；
- `07_report.json`；
- `07_report.md`；
- `07_render_metrics.json`；
- `07_pipeline_metrics.json`。

## 5. 案例与运行目录

所有核验产物位于：

```text
backend/data/trust/cases/<case_id>/
├── input.json
├── latest_run.json
└── runs/
    └── <run_id>/
        ├── run.json
        ├── 00_input.json
        ├── 01_claims.json
        ├── 02_*.json
        ├── 03_*.json
        ├── 04_*.json
        ├── 05_evidence_ledger.json
        ├── 05_attempts/
        ├── 06_report_draft.json
        ├── 06_attempts/
        └── 07_*.json / 07_report.md
```

`case_id` 生成规则：

- 有来源 URL：对 URL 做 SHA-256，取前 16 位，格式为 `video-<digest>`；
- 无来源 URL：对规范化主张 JSON 做 SHA-256，取前 12 位，格式为 `case-<digest>`。

`run_id` 使用 UTC 高精度时间戳。同一案例每次执行创建新的不可变运行目录，`latest_run.json` 只保存最近完成到哪一阶段，不覆盖历史运行。

`run.json` 记录每阶段状态、开始时间、耗时、产物、指标和错误。即使中途失败，已经完成的阶段产物仍然保留，便于人工定位。

## 6. 性能、并发与重试

### 6.1 LLM 调用构成

不含上游内容提取时，下游调用构成为：

1. M2：1 次规划调用；
2. M5：1 至多个并发初筛批次；
3. M6：1 次报告调用，验证失败时最多按配置重试。

M1、M4、M7 不调用 LLM，M3 只调用 Exa。

### 6.2 快速与高质量

| 档位 | M2 | M5 | M6 | 查询与证据 |
|---|---|---|---|---|
| `speed` | MiMo 2.5，关闭思考 | MiMo 2.5 Pro，关闭思考 | MiMo 2.5 Pro，关闭思考 | 完全保留 |
| `quality` | MiMo 2.5，关闭思考 | MiMo 2.5 Pro，关闭思考 | MiMo 2.5 Pro，开启思考 | 与 speed 相同 |

档位不会减少搜索数量、Exa 返回数、证据池或 M5 覆盖范围。质量档只增加 M6 的推理能力，因此两个档位可以公平比较速度和终判质量。

### 6.3 超时隔离

- M3：每个 Exa 任务独立超时；
- M5：每个模型批次独立请求，批次并发；
- M6：独立报告超时，失败只重试 M6；
- SSE：仅发送阶段事件，不发送模型 token，不影响 JSON 完整性。

### 6.4 当前并发边界

`verify_structured_information` 当前使用进程内 `asyncio.Lock` 串行化完整核验运行，避免多个请求共享进程状态时造成审计指标或运行文件串线。锁内的 M3 查询和 M5 批次仍然并发。

多进程部署时锁不跨进程。若未来需要同一进程同时执行多个案例，应先将所有阶段用量状态彻底改为 run-local，再移除该锁，而不是直接放开并发。

## 7. API 与 SSE 协议

### 7.1 Web 同步接口

- `POST /api/analyze`：URL/分享输入，全链路或仅提取；
- `POST /api/analyze/upload`：文字及文件上传；
- `POST /api/verify`：直接提交 `structured_data` 重新核验。

请求中的核验档位：

```json
{
  "url": "https://example.com/content",
  "verification_mode": "speed",
  "verify": true
}
```

### 7.2 Web 阶段 SSE

- `POST /api/analyze/stream`：URL/分享输入；
- `POST /api/analyze/upload/stream`：文字/文件输入。

进度事件：

```text
event: progress
data: {"type":"progress","message":"M3 并发检索执行"}
```

结果事件：

```text
event: result
data: {"type":"result","data":{...完整 AnalyzeResponse...}}
```

错误事件：

```text
event: error
data: {"type":"error","message":"错误说明"}
```

### 7.3 Android Job API

创建任务时新增：

```json
{
  "source": {"type":"shared_url","value":"https://example.com/video"},
  "mode": "auto",
  "verification_mode": "quality",
  "client_request_id": "客户端幂等编号"
}
```

Job Worker 将内部 M1–M7 消息映射到稳定的公开 `JobStage` 和进度百分比。`GET /v1/jobs/{job_id}/events` 保留 `Last-Event-ID` 与单调序号语义，断线重连不会倒退进度。

完成结果继续包含轻量 `card`，同时在 `analysis.verification` 返回完整逐主张核验、叙事分析、待补证据和关键依据。

## 8. Web 与 Android 展示

### 8.1 Web

Web 工作台新增：

- 快速核验 / 质量核验选择；
- 链接和纯文字统一阶段进度；
- 综合判定和传播建议；
- 逐主张结论、充分度、说明和不确定性；
- 叙事分析；
- 待补证据；
- 关键依据链接；
- 完整报告 JSON；
- 搜索计划、阶段耗时、token 和费用摘要。

静态资源版本已提升，避免浏览器继续使用旧 JS/CSS 缓存。

### 8.2 Android

Android 请求 DTO、Job 模型和数据库均增加 `verification_mode`。新版 Compose 对话页通过 Chip 选择快速或高质量，分享面板和未显式选择的调用默认使用 `speed`。

Android 完成任务后，从 `analysis.verification` 提取并持久化四组轻量文本：

- `claimDetails`：逐主张核验；
- `narrativeAnalysis`：叙事分析；
- `evidenceGaps`：待补证据；
- `keyEvidence`：关键依据标题和 URL。

Room 数据库从 v1 升级到 v2，通过 `MIGRATION_1_2` 新增四列，不删除旧任务。详情页字段为空时保持向后兼容，只展示原结论卡和时间线。

本次改动已与远端“悬浮核验球、超级岛、新版 Compose 导航”代码合并：保留新版 UI 和悬浮球交互，同时加入核验档位、M1–M7 进度及完整报告区块。

## 10. 兼容性与迁移

### 10.1 后端缓存

缓存版本更新为：

- Schema：`compact-claims-v2`；
- Pipeline：`m1-m7-v1`。

启动时会清理不属于当前协议的历史缓存，避免旧字段继续流入新流水线。已有 M1–M7 运行目录可以通过 `case_id + run_id` 恢复完整报告。

### 10.2 Job 数据库

服务端 SQL Job 表新增 `verification_mode VARCHAR(10) NOT NULL DEFAULT 'speed'`。初始化时检查现有列，缺失则原地 `ALTER TABLE`，旧任务自动按 `speed` 解释。

### 10.3 Android Room

Android Room 从 v1 升至 v2，只增加可空报告详情列，不执行 destructive migration。

### 10.4 破坏性协议变化

任何仍发送旧 `原子主张/隐性观点` JSON 的客户端必须升级为 `主题/主张[{文本,表达}]`。本仓库 Web、Job Worker 和 Android DTO 已同步升级。

## 12. 已知边界

- 系统是快速事实核查与传播风险粗筛，不是司法、医学或学术终审；
- 搜索只执行一轮，没有二次补搜，缺少关键材料时必须如实输出待补证据；
- Exa 返回的 highlights 可能缺少完整上下文，M5/M6 必须避免把摘录强度扩大；
- 多家媒体转述同一原始说法不等于多份独立证据；
- 模型可利用一般知识理解术语和设计核验方法，但结论必须落到本次证据；
- `隐含` 表示内容形成的叙事引导，不代表系统已经认可该指控；
- 当前进程内核验串行锁限制了多案例并发吞吐，扩容优先使用 Worker 多进程，并在移除锁前完成 run-local 状态改造；
- Android 完整构建必须在具备 SDK 的环境验证，Python 的源码契约测试不能替代 Kotlin 编译。

## 13. 后续维护规则

修改模块时遵循以下约束：

1. 不跨阶段偷偷读取未声明文件；
2. 新增模型输入必须保存实际请求和原始响应；
3. 新增字段同时更新验证器、报告渲染、Web、Job DTO、Android DTO 和测试；
4. 不通过减少查询数量或丢弃证据换取性能；
5. 不添加针对具体案例、人物、学校、疾病或谣言文本的判断分支；
6. M6 重试必须复用 M1–M5，不重新产生搜索费用；
7. 新的搜索提供方必须先统一为 M3 原始任务协议，再进入 M4；
8. 所有对外进度文案应从模块事件映射，不暴露模型内部思考；
9. 协议不兼容变更必须提升缓存 Schema/Pipeline 版本并提供迁移说明；
10. 提交前至少运行全量 Python 测试、JS 语法检查和差异格式检查。
