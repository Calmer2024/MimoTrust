# MiMo Trust 双系统架构对比与接入方案

> 本文档完整梳理 Demo（`mimotrust/`）与生产（`MimoTrust/`）两套系统的架构、协议、管道和接口差异，作为后续"Demo 管道接入生产 Job 系统"的决策基础。

---

## 1. 总体定位

| | Demo (`mimotrust/`) | 生产 (`MimoTrust/`) |
|---|---|---|
| 定位 | 事实核查算法原型，验证 M1-M7 七阶段管道 | 落地产品，对接"小真"Android App 和小米超级岛 |
| 前端 | 内置静态 HTML/JS 单页应用 | 无独立前端；Android App 通过 Job API 对接 |
| 部署 | 单进程 uvicorn | Docker Compose（PostgreSQL + Redis + MinIO + ARQ Worker） |
| 运行模式 | 仅同步 `/api/analyze` | 同步 `/api/analyze` + 异步 `/v1/jobs` 双轨 |

## 2. 结构化数据协议

### 2.1 Demo 协议：`compact-claims-v2`

```python
# app/models.py — Demo
class ExtractedClaim(BaseModel):
    text: str     # alias="文本"，8~300字，必须含中文
    expression: Literal["直接", "转述", "隐含"]  # alias="表达"

class StructuredInformation(BaseModel):
    topic: str              # alias="主题"
    claims: list[ExtractedClaim]  # alias="主张"
```

协议版本：`compact-claims-v2`

示例：
```json
{
  "主题": "武汉一位女性献血者长期高频献血事迹",
  "主张": [
    {"文本": "一位武汉女性自2004年起已累计献血300次", "表达": "直接"},
    {"文本": "视频发言者暗示该献血记录可能造假", "表达": "隐含"}
  ]
}
```

特点：
- 每条主张是结构化对象，带 `表达` 分类（直接/转述/隐含）
- 无 `case_id` 字段，运行时由内容哈希生成
- 隐含主张独立建模，不混入原子主张

### 2.2 生产协议：`structured-information-v4`

```python
# app/models.py — 生产
class StructuredInformation(BaseModel):
    case_id: str           # pattern: ^[a-z0-9]+(?:-[a-z0-9]+)*$
    content_topic: str     # alias="内容主题"
    atomic_claims: list[str]     # alias="原子主张"，纯字符串列表
    implicit_opinions: list[str] # alias="隐性观点"，纯字符串列表
```

协议版本：`structured-information-v4`

示例：
```json
{
  "case_id": "wuhan-blood-donor-300-times",
  "内容主题": "武汉一位女性献血者长期高频献血事迹",
  "原子主张": [
    "一位武汉女性自2004年至2008年1月期间开始在武汉市血液中心进行成分献血，截至视频发布时已累计献血300次。"
  ],
  "隐性观点": [
    "视频发言者对该献血者的高频献血行为表达了崇拜与赞叹"
  ]
}
```

特点：
- 主张是纯字符串，无表达分类
- 有显式 `case_id`
- 原子主张和隐性观点分两个数组

### 2.3 协议桥接要点

| 维度 | Demo → 生产 | 生产 → Demo |
|---|---|---|
| 主张格式 | `{文本, 表达}` 对象 → 纯字符串（丢弃 `表达`） | 纯字符串 → `{文本, 表达}` 对象（需推断或默认"直接"） |
| `case_id` | 无 → 需从内容哈希生成 | 已有 → 直接使用 |
| 隐含主张 | `claims` 中 `表达=="隐含"` → 移入 `implicit_opinions` | `implicit_opinions` → 移入 `claims` 并标记 `表达="隐含"` |

## 3. 事实核查管道

### 3.1 Demo 管道：M1-M7 七阶段模块化

位置：`app/trust/pipeline_v2/`

```
M1 输入规范化 → M2 检索规划 → M3 并发检索 → M4 证据池归一化
→ M5 证据初筛 → M6 最终研判 → M7 报告渲染
```

各阶段详情：

| 阶段 | 模块 | 输入 | 输出 | 是否调用 LLM |
|---|---|---|---|---|
| M1 | `normalization.py` | 原始 JSON | `01_claims.json`（C1/C2 编号） | 否 |
| M2 | `planning.py` | `01_claims.json` | `02_verification_plan.json`（V1/Q1 编号） | 是（mimo-v2.5） |
| M3 | `retrieval.py` + `search_providers.py` | `02_verification_plan.json` | `03_retrieval.json` | 否（Exa API） |
| M4 | `evidence.py` | `03_retrieval.json` | `04_evidence_pool.json`（E1 编号，URL 去重） | 否 |
| M5 | `evidence_triage.py` | 证据池 + 核验计划 | `05_evidence_ledger.json`（七列紧凑账本） | 是（mimo-v2.5-pro） |
| M6 | `synthesis.py` | 账本 + 全文证据 | `06_report_draft.json`（o/c/n/g 紧凑格式） | 是（mimo-v2.5-pro，thinking=enabled） |
| M7 | `rendering.py` | 报告草稿 + 证据池 | `07_report.json` + `07_report.md` | 否 |

关键设计：

- **CaseRunWorkspace**：每次运行在 `data/trust/cases/{case_id}/runs/{run_id}/` 下保存完整中间产物
- **严格接口校验**：每个阶段对输入输出做 Pydantic + 自定义校验，不合法即抛异常
- **紧凑编码**：M5 用七列数组 `[E编号, 来源性质, 独立性, 关系, 终判输入, 重复自, 关键信息]`，M6 用 `{o, c, n, g}` 四键
- **LLM 计时**：每次调用记录 `response_id`、`model`、`finish_reason`、token 用量，写入阶段 metrics
- **模型配置**：`MIMO_PLANNING_MODEL`、`MIMO_TRIAGE_MODEL`、`MIMO_REPORT_MODEL` 可独立配置
- **重试**：M6 失败时可重试（`MIMO_REPORT_MAX_ATTEMPTS`），M5 失败批次降级为全文

入口函数：

```python
# app/trust/service.py — Demo
async def verify_structured_information(
    structured: StructuredInformation,
    verification_mode: Literal["speed", "quality"] = "speed",
    source_url: str | None = None,
    progress: ProgressCallback | None = None,
) -> dict[str, Any]
```

### 3.2 生产管道：四阶段流程

位置：`app/trust/pipeline.py`

```
step1 检索规划 → step2 多源并发检索 → step3 证据语义初筛 → step4 报告生成
```

各阶段详情：

| 阶段 | 函数 | 输入 | 输出 | 是否调用 LLM |
|---|---|---|---|---|
| 1 | `step1_construct_search_plan` | 案例 JSON | `01_search_plan.json`（web_queries + evidence_contracts） | 是（mimo-v2.5） |
| 2 | `step2_execute_search` | 检索计划 | `02_retrieval.json` + `03_evidence.json`（tier1/2/3 分级） | 否（Exa + OpenAlex + ArXiv + Wikipedia + Semantic Scholar） |
| 3 | `step3_assess_evidence` | 证据 + 主张 | `03_evidence_assessed.json`（紧凑账本 + 源评估） | 是（mimo-v2.5，批量 triage） |
| 4 | `step4_generate_report` | 评估后证据 | `04_report.json` + `04_report.md` | 是（mimo-v2.5-pro，thinking 可选） |

关键设计：

- **CaseRunWorkspace**：同 Demo，保存在 `data/trust/cases/{case_id}/runs/{run_id}/`
- **全局 LLM_CALL_TIMINGS**：进程级列表，记录所有 LLM 调用（Demo 的 M1-M7 每阶段独立 metrics）
- **Evidence Contracts**：每个主张有 `claim_type`、`required_evidence`、`risk_flags`，驱动证据门槛判定
- **多源检索**：除 Exa 外接入 OpenAlex、ArXiv、Wikipedia、Semantic Scholar
- **Tier 分级**：检索结果自动分为 tier1（高信任）、tier2（支撑）、tier3（孤立）
- **Evidence Policy**：`evidence_policy.py` 包含复杂的证据满足判定、事件独立佐证、排他性挑剔检测等规则
- **风险姿态**：硬编码 `REPORT_RISK_POSTURE_PROMPT`，保守放行策略

入口函数：

```python
# app/trust/service.py — 生产
async def verify_structured_information(
    structured: StructuredInformation,
    stage_callback: Callable[[str], Awaitable[None]] | None = None,
) -> dict[str, Any]
```

### 3.3 管道对比

| 维度 | Demo M1-M7 | 生产四阶段 |
|---|---|---|
| 阶段数 | 7（M1 规范化、M2 规划、M3 检索、M4 归一化、M5 初筛、M6 研判、M7 渲染） | 4（规划、检索、初筛、报告） |
| LLM 调用数 | 3~4 次（M2 + M5 批次 + M6，可重试） | 3 次（step1 + step3 批次 + step4） |
| 搜索源 | 仅 Exa | Exa + OpenAlex + ArXiv + Wikipedia + Semantic Scholar |
| 证据归一化 | M4 独立阶段，URL 去重合并 | 合并在 step2 |
| 初筛编码 | 七列紧凑数组（来源性质/独立性/关系/终判输入/重复自/关键信息） | 自由格式（source_role/claim_relations/evidence_strength） |
| 报告格式 | `{o, c, n, g}` 紧凑四键 → M7 展开渲染 | 直接输出完整 JSON |
| 证据门槛 | 无 evidence_contract，靠 LLM prompt | 显式 evidence_contract + evidence_policy 规则引擎 |
| 中间产物 | 每阶段独立文件，含 input/output/metrics | 合并文件，含 raw_model_output |
| 接口校验 | 严格（每个阶段独立 validator） | 宽松（主要靠 LLM 输出解析 + normalize） |
| 计时方式 | 每阶段独立 metrics JSON | 全局 `LLM_CALL_TIMINGS` 列表 |

## 4. 内容提取层

### 4.1 Demo

位置：`app/pipeline.py`

支持平台：抖音、B站、YouTube

流程：
```
URL → yt-dlp/Playwright 提取元数据 → 字幕下载 → 音频 ASR（分段并发）
→ 关键帧 OCR（场景变化 + 周期） → 全视频多模态升级（L3）
→ 结构化信息转换（MiMo LLM） → AnalyzeResponse
```

成本阶梯：L0（缓存/元数据）→ L1（字幕）→ L2（ASR/OCR/结构化）→ L3（全视频多模态）

支持平台：抖音、B站、YouTube、快手、微博、小红书、视频号、任意文章 URL、多模态上传

新增能力：
- **文章提取**：`analyze_article_url()` — BeautifulSoup 提取正文
- **多模态上传**：`analyze_upload_bundle()` — 文本+图片+音频+视频混合输入
- **视频号适配**：`channels.py` — 页面解析 + API feed 获取
- **快手适配**：`kuaishou.py`
- **微博适配**：`weibo.py`
- **小红书适配**：`xiaohongshu.py`
- **封面转存**：`thumbnails.py` — 稳定化外部封面 URL

## 6. 移动端 Job 系统（生产独有）

### 6.1 架构

```
POST /v1/jobs → JobRuntime.create()
  ├─ memory 模式：MemoryJobStore + MemoryEventBus + asyncio.create_task(process_job)
  └─ distributed 模式：SqlJobStore(PostgreSQL) + RedisEventBus(Redis) + ARQ Worker
```

### 6.2 数据模型

```python
class CreateJobRequest(BaseModel):
    source: JobSource          # type: shared_url | agent_context | platform_api
    mode: Literal["auto", "visual"]
    client_request_id: str     # 幂等键

class JobView(BaseModel):
    job_id: str
    device_id: str
    status: JobStatus          # queued | running | completed | failed | cancelled
    stage: JobStage            # queued | content_resolving | media_extracting | ...
    display_text: str          # 用户可见文案
    progress_hint: int         # 0~100 流程完成度
    sequence: int              # 单调递增，防乱序
    result: dict | None        # MobileResultCard + 完整分析
    ...

class MobileResultCard(BaseModel):
    job_id: str
    verdict: str               # 属实/部分属实/误导/虚假/证据不足/待核实
    headline: str              # 用户可见结论
    conclusion: str            # 不超过80字摘要
    evidence_count: int
    key_evidence: list[EvidenceSummary]
    uncertainty_note: str | None
    report_url: str | None
    ai_disclaimer: str = "AI 辅助核验，仅供信息参考"
```

### 6.3 Worker 流程

```python
async def process_job(runtime, job_id):
    # 1. content_resolving → media_extracting
    result = await analyze_content(AnalyzeRequest(...))  # 复用内容提取

    # 2. claim_structuring
    emit(f"已识别 {N} 条待核验主张")

    # 3. evidence_retrieval → evidence_triage → report_generating
    result.verification = await verify_structured_information(
        result.structured_data,
        stage_callback=on_stage,  # 管道每阶段回调
    )

    # 4. completed
    card = build_mobile_card(job_id, result, completed_at)
    emit(result=card + analysis)
```

### 6.4 事件协议

```json
{
  "event_id": "uuid",
  "job_id": "uuid",
  "sequence": 4,
  "stage": "evidence_retrieval",
  "state": "running",
  "display_text": "正在比对公开来源",
  "elapsed_ms": 18320,
  "progress_hint": 55,
  "occurred_at": "2026-08-01T10:00:18+08:00"
}
```

## 8. 接入方案分析

### 方案 A：Demo M1-M7 管道替换生产管道

**做法**：将 `pipeline_v2/` 整体移入生产，替换 `trust/pipeline.py`，适配 `StructuredInformation` 协议。

| 优势 | 风险 |
|---|---|
| M1-M7 模块化更清晰，每阶段独立校验和 metrics | 需要适配 `原子主张`/`隐性观点` → `主张` 对象的协议转换 |
| 七列紧凑账本编码更规范 | 失去生产版的多源检索（OpenAlex/ArXiv/Wikipedia/Semantic Scholar） |
| M6 紧凑输出减少 token 用量 | 失去 evidence_contract + evidence_policy 规则引擎 |
| M7 独立渲染，报告格式更稳定 | 需要验证 Job 系统的 `stage_callback` 与 M1-M7 的对接 |

改造量：
- `trust/service.py`：改为调用 `run_full_pipeline()` 替代 `run_pipeline()`
- `trust/pipeline.py`：替换为 `pipeline_v2/pipeline.py`
- `StructuredInformation`：需要协议桥接层（2.3 节）
- `models.py`：`AnalyzeResponse.structured_data` 字段类型需要兼容两套协议
- `jobs/worker.py`：`STAGE_DETAILS` 映射需要从 4 阶段改为 7 阶段

### 方案 B：保留生产管道，接入 Job 系统

**做法**：Demo 的 M1-M7 不进入生产，生产继续用四阶段管道。Demo 前端改为调用 `/v1/jobs` 替代 `/api/analyze/stream`。

| 优势 | 风险 |
|---|---|
| 生产管道已验证，多源检索和 evidence_contract 保留 | M1-M7 的模块化优势不进入生产 |
| 改造量最小 | Demo 前端需要重写为 Job 轮询/SSE 模式 |
| Job 系统已就绪 | 两套管道继续并行维护 |

改造量：
- Demo `app/static/app.js`：`streamAnalysis()` 改为 `POST /v1/jobs` + SSE 轮询
- Demo `app/main.py`：挂载 `jobs_router`，配置 `MIMO_JOB_MODE=memory`

### 方案 C：混合方案 — 用 Demo M5/M6 替换生产 step3/step4

**做法**：保留生产 step1（多源检索规划）和 step2（多源并发检索），用 Demo 的 M5（证据初筛）和 M6（最终研判）替换生产 step3 和 step4。

| 优势 | 风险 |
|---|---|
| 保留多源检索能力 | 需要将生产 tier 分级证据适配为 Demo M4 证据池格式 |
| 获得 M5 七列紧凑账本和 M6 紧凑输出 | 两套管道的证据 ID 体系不同，需要映射 |
| M6 的 `{o, c, n, g}` 输出更省 token | evidence_policy 规则引擎与 M6 prompt 可能冲突 |

改造量：
- 新增适配层：生产 `step2` 输出 → Demo `M4` 证据池格式
- 替换 `step3` → `M5`，`step4` → `M6`+`M7`
- `trust/service.py` 重写

## 9. 建议

在选择方案前，需要明确：

1. **多源检索是否必须保留？** 生产版接入了 OpenAlex/ArXiv/Wikipedia/Semantic Scholar，Demo 只有 Exa。如果这些源对核验质量有实质贡献，方案 A 需要额外补齐。
2. **evidence_contract 规则引擎是否必须保留？** 生产版有显式的证据门槛规则（定量比较需原始数据、事件需独立佐证等），Demo 主要靠 LLM prompt 隐式约束。
3. **Demo 前端是否需要保留？** 如果 Demo 前端只是开发调试用，方案 B 最简单；如果 Demo 前端也要给用户用，需要接入 Job 系统。
4. **维护成本容忍度？** 两套管道长期并行维护成本高，方案 A/C 有助于统一。
