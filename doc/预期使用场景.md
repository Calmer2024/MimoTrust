## 1. 受控短视频应用

比赛阶段开发一款最小化的受控短视频应用，用于完整验证“浏览内容—后台核验—传播前提示—展开证据”的产品闭环。

应用不设置复杂的账号、推荐和视频发布系统，也不要求用户上传视频。系统预置少量公开且已获得使用许可的演示视频，并提供基础的上下滑动浏览、点赞、评论和转发功能。为演示分享场景，应用内预置少量虚拟联系人，但不实现真实社交关系和消息服务。

视频由团队提前存储在公网可访问的对象存储中。经用户开启信息核验功能并授权后，短视频应用可向信源守护者提供当前内容上下文，包括：

```
{
  "source_app": "controlled_video_app",
  "content_id": "video-001",
  "content_version": "v1",
  "content_hash": "...",
  "video_url": "https://storage.example.com/video-001.mp4",
  "title": "视频标题",
  "author": "发布账号",
  "published_at": "2026-07-27",
  "position_ms": 3500,
  "duration_ms": 45000
}
```

该受控应用模拟获得系统级当前内容接口后的运行环境，但不宣称已经具备读取抖音、B站等第三方应用视频的能力。

### 2. 触发式分析与缓存机制

用户授权后，普通浏览、播放和页面停留不向信源守护者提交分析任务。只有用户打开评论面板、打开转发面板，或主动通过守护者入口发起核验时，客户端才提交当前内容上下文。沙盒不设置 1.5 秒或其他停留阈值，也不根据停留行为自动预分析。

系统首先根据以下信息查询缓存：

```
来源应用 + 内容 ID + 内容版本/哈希 + 模型版本 + 核验流程版本
```

若存在仍在有效期内的核验报告，则直接返回缓存结果，并展示报告生成时间。若缓存已过期，系统可以先展示历史结果，同时在后台重新核验。系统不将未经校验的普通模型回复直接作为缓存结果。

触发后未命中缓存时，由团队自建的核验编排服务执行以下流程：

1. 将公网可访问的视频 URL、标题和来源信息提交给 MiMo-V2.5；
2. MiMo 联合理解视频画面、语音、字幕和标题；
3. 提取1至3条带视频时间位置的原子主张；
4. 信源检索与溯源子 Agent 为每条主张生成检索计划；
5. 检索服务获取候选来源，并进行正文固化、时间记录和转载去重；
6. 证据分析模块判断材料对主张构成支持、反驳、限定、背景或无关；
7. 报告生成模块在已有证据范围内形成核验结果；
8. 程序化校验引用、链接、时间和结论强度后，生成可展示报告。

MiMo 是多模态内容理解、主张拆分和证据语义判断的核心；任务调度、搜索、缓存、来源固化和结果校验由后端编排服务负责。

### 3. 场景内提示

用户正常浏览时，系统不自动启动分析，也不显示虚假的预分析状态。当用户评论、转发或主动触发信源守护者时，客户端提交当前上下文并读取缓存或任务状态：

- 缓存命中或分析完成：展示简明核验卡片；
- 分析仍在进行：展示“正在核对来源，可继续当前操作”；
- 内容获取失败：说明无法取得完整视频，并提供替代输入方式；
- 证据不足：明确展示“暂缺足够证据”，不生成确定性结论。

主动触发入口可以在原型中表现为核验按钮或悬浮球。侧边栏和小爱同学唤起作为未来 HyperOS 集成方式展示，不宣称已经接入相关系统接口。评论触发不读取用户输入的评论内容；评论或转发触发均不阻塞原操作。

### 4. 外部应用兼容场景

在抖音、B站等外部应用中，用户可以通过系统分享将链接发送给信源守护者。系统分享通常只提供页面链接，并不直接提供视频文件，因此需要经过内容接入适配器处理：

```
系统分享链接
→ 识别平台并解析规范化页面地址
→ 尝试取得公开且经过授权的视频媒体
→ 流式转存或上传至临时对象存储
→ 生成短期签名 HTTPS URL
→ 提交给 MiMo
```

该方式仅处理公开可访问、无需绕过登录或 DRM 保护的内容。临时媒体应设置访问期限和自动删除机制，不长期保存用户提交的视频。

当分享链接无法取得完整视频时，系统应明确降级：

- 使用平台公开提供的标题、字幕、封面和页面信息进行有限分析；
- 允许用户选择本地视频、截图或文本；
- 在报告中标明实际分析范围；
- 不根据未获取的内容生成完整视频结论。

比赛阶段，外部平台链接解析属于兼容性实验能力，不作为现场主演示的必要依赖。

### 5. 文章、图文与图片

对于系统分享直接提供的文字、图片或文件，信源守护者可以在完成授权和完整性检查后，将内容提交给对应的多模态理解模块。

如果系统分享只提供网页链接，则需要先判断页面是否公开可访问、是否需要登录、正文是否完整以及内容是否动态加载。只有成功取得的部分才能进入原子主张提取流程。若正文、配图或来源信息缺失，报告必须标注缺失范围，不能将部分内容视为完整原文。

## 场景内悬浮提示

信源守护者提供醒目但非打断式的悬浮球，作为浏览过程中核验状态的统一入口。悬浮球不遮挡视频主体、评论输入框和转发按钮，用户可以忽略、拖动或关闭。

在受控短视频应用中，当用户进入评论区域、点击转发或主动发起核验时，客户端读取当前视频的分析状态，并提高对应核验任务的处理优先级。若已有核验结果或状态发生变化，悬浮球通过一次短暂跳动、轻微放大或状态角标吸引注意，但不阻止用户继续评论或转发。

在抖音、B站等外部平台中，普通应用无法直接感知平台内部的评论行为。只有在用户调用系统分享、通过侧边栏或小爱同学主动唤起

动画只在状态发生变化时短暂播放，不持续闪烁；同时支持关闭动画和减少动态效果，以避免干扰浏览及影响无障碍体验。点击悬浮球后，展开核验卡片，展示原内容主张、视频位置、主要证据、来源链接、核验时间和未确认部分。

比赛原型中的悬浮球作为受控短视频应用内部组件实现，不需要申请跨应用悬浮窗权限；未来接入 HyperOS 后，可以由系统级可信内容服务提供跨应用的一致入口。

## 兼容输入入口

除当前内容自动获取外，信源守护者还提供独立的兼容输入页面，用于无法取得当前内容或未接入系统能力的场景。用户可以主动提交：

- 本地视频文件；
- 图片、截图和长图；
- 文章文件或网页链接；
- 纯文字和剪贴文本；
- B站、抖音及其他平台的分享链接；
- 由其他应用通过系统分享导出的媒体或文本。

系统在接收内容后先执行格式、大小、可访问性和完整性检查，再进入对应的多模态理解与原子主张提取流程。若只取得部分内容，应明确标注实际分析范围；若链接需要登录、已经失效或无法取得媒体，不绕过平台限制，而是提示用户改用本地文件、截图或文字输入。

因此，产品形成两类互补入口：

```
低操作入口：
当前内容上下文 → 后台分析 → 悬浮提示

兼容入口：
用户主动上传/分享/粘贴 → 完整性检查 → 分析报告
```

前者体现未来系统级接入的体验优势，后者保证在缺少平台或系统支持时，信源守护者仍然是一款可以独立使用的完整应用。
